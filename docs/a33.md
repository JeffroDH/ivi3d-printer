# A33 touchscreen board

The Allwinner A33 module runs the touchscreen UI, Wi-Fi, and the kore HTTP server. Motion stays on the STM32; the link is `/dev/ttyUSB0` at 115200 8N1. See [architecture.md](architecture.md).

Tags: **[V]** image, boot log, or live capture · **[I]** inferred · **[U]** unknown.

Stock UI binary in this repo: `firmware/Firmware/firmware` (same file as `/userapp/app/IVI-Main-Controller`, version **1.222**). Qt **5.9.6** under `/opt/qt-5.9.6`. Kernel **3.4.39**, `machine=sinlinx`, product string "sun8i linux".

## Boot chain

```
BROM
  → boot0  eGON.BT0 v3.1.0 at 8 KiB in the eMMC boot area (checksum valid)
  → U-Boot 2011.09 at sector 38192, script.bin appended, bootdelay=0, work_mode=0
  → partition 6 Android boot image: kernel 3.4.39 + gzip ramdisk
  → /init: e2fsck -y on mmcblk0p7, mount rw, switch_root
  → inittab: ttyS2 root shell (no login) → /etc/profile → autorun.sh → IVI-Main-Controller
```

`rcS` does not run the `S??*` init scripts, so `S50sshd` never starts **[V]**.

boot0 brings up only the card the BROM handed it. On failure it jumps to FEL (`0xffff0020`). It contains no MMC write or erase opcodes **[V]**. Stock U-Boot with `work_mode=0` initialises only the boot medium. Card-burn mode is `work_mode=0x11` plus a vendor image that this project does not have **[V]**.

U-Boot's "Try SD card 2 / Try MMC card 2" lines are a protocol retry on the eMMC controller, not a microSD boot attempt **[V]**.

The A33 manual's BROM order is SDC0 (microSD) → NAND → SDC2 (eMMC) → SPI → FEL **[D]**. Whether this board's BROM actually tries the microSD socket first has not been observed **[U]**. There is no NAND. `boot_recovery` has no recovery partition and no misc, so it does not boot a recovery image **[V]**.

DRAM on this unit is 512 MiB. eMMC is about 3.69 GiB (`mmcblk0`, MMC 004GA0) plus two 2 MiB hardware boot areas. boot1 was all `0x00` in the backup **[V]**.

| Partition | Filesystem | Mount / role |
|---|---|---|
| p1 | FAT32 | `/userdata/WifiFile` (UDISK, Wi-Fi uploads) |
| p2 | FAT16 | boot-res / logos |
| p5 | env | U-Boot environment |
| p6 | boot image | kernel + ramdisk |
| p7 | ext4, 512 MiB | rootfs, `root=/dev/mmcblk0p7` |

`e2fsck -y` runs on p7 at every boot. The rootfs is mounted `barrier=0` **[V]**. A power cut during a rootfs write is a real risk. If p1 fails to mount, autorun can `mkfs.vfat` it.

## Console

`console=ttyS2,115200` and `script.bin` `[uart_para]` port 2 on **PB0/PB1** **[V]**. On this unit that console is the rear `DEBUGUART_*` pads and the front 3-pin (owner continuity **[O]**; a full boot and a root shell were captured at 115200 8N1 **[V]**).

Adapter: USB-TTL at 3.3 V, **VCC left open**, RX/TX crossed, GND common. Open the terminal before applying power. The UI process sends stdout and stderr to ttyS2, so application logs appear on this port.

The redacted capture is [research/a33_uart_boot_20261107.log](research/a33_uart_boot_20261107.log).

| Item | Value |

| Display | `QT_QPA_PLATFORM=linuxfb:fb=/dev/fb0`, `QWS_SIZE=800x480` |

The profile selects the highest existing `event4`…`event1` node. A live session used `event3` **[V]**. Qt does not grab the evdev node, so a second writer can inject events. Geometry of the on-screen controls is [data/tap_geometry.csv](data/tap_geometry.csv). The navigator that uses it is [wifi_touch.md](wifi_touch.md).

## sshd

`/usr/sbin/sshd` is OpenSSH **5.8p1**, ARMv7 soft-float, and its libraries are on the rootfs **[V]**. Nothing starts it:

- `/sinlinx/sshd start` is commented out in `autorun.sh`.
- `S50sshd` is never run.
- No host keys exist under `/etc/ssh`.
- A LAN scan shows port 22 closed.

The stock `sshd_config` is the commented template, so compiled defaults apply (`PermitRootLogin yes`, `PasswordAuthentication yes`). The root account has a password set (MD5-crypt); the password is not known and is not recorded here.

Two library/path issues block a naive start **[I]**, confirmed against the binary's search path and the modes on disk:

- `LD_LIBRARY_PATH=/opt/qt-5.9.6/lib` (set for the UI) makes sshd load the wrong OpenSSL. Start it with `LD_LIBRARY_PATH=` empty.
- `/var/empty` is mode 0777, which privilege separation rejects. Either `chmod 755 /var/empty` or `-o UsePrivilegeSeparation=no`.

`/root` does not exist, so `/root/.ssh/authorized_keys` cannot be used until that directory is created. The session procedure keeps the host key, the authorized key, and the pid file under `/tmp` and does not edit the rootfs. Steps: [home_session/RUNBOOK.md](home_session/RUNBOOK.md).

A login shell (`ssh` with no remote command) reads `/etc/profile` and will start a **second** `IVI-Main-Controller`. Every SSH command must be non-login (`ssh -T … -- 'command'`).

## kore upload API

kore listens on `<wlan0>:8080` with TLS off, started by `timeStartKore.sh` once wlan0 has an address. Routes in the on-disk config and `printer_http_api.so` **[V]**:

| Method and path | Behaviour |
|---|---|
| `POST /api/v1/connect` | Session token |
| `POST /api/v1/disconnect` | |
| `GET /api/v1/status` | Static `{"status":"IDLE"}` |
| `POST /api/v1/setSystemTime` | Sets the clock |
| `POST /api/v1/upload` | Writes `/userdata/WifiFile/<name>` |
| `POST /api/v1/sliceUpload` | Chunked upload under `tmp_files/`, MD5 checked |

There is no firmware-update route and no print-start route. `prepare_print`, `start_print`, `pause_print`, `resume_print`, and `stop_print` return **404** on this firmware (live test, see [network.md](network.md)).

`POST /api/v1/upload` reads only the multipart part named `file`. A missing part is **412** `file err`. The filename is copied into a 128-byte buffer and split on `.`. Empty pieces are skipped, and at most two pieces are kept. The second piece must be exactly `gcode`, `cnc`, or `nc` (case-sensitive `strcmp`). Anything else is **412** `File type error`. The file is written to `/userdata/WifiFile/<name>` and an existing file of that name is overwritten. A name with no dot leaves the second piece null.

| Name | Result |
|---|---|
| `cube.gcode`, `cube..gcode` | **201** `Upload successfully` (same name is overwritten) |
| `a.gcode.bak` | **201**. The second piece is `gcode`, so the name is stored as given |
| `benchy_0.2mm.gcode`, `Cube_0.2mm_PLA.gcode` | **412** `File type error` |
| `x.GCODE`, `x.g` | **412** `File type error` |

The bridge rewrites Wi-Fi names before this call. Extra dots and characters outside `[A-Za-z0-9_-]` become `-`, the extension is folded to `gcode`, `cnc`, or `nc`, and the result is capped at 100 bytes. `Cube_0.2mm_PLA.gcode` is uploaded as `Cube_0-2mm_PLA.gcode`. Two different originals that land on one name get `-2`, `-3`, and so on. USB streaming keeps the slicer's name. See [bridge/README.md](../bridge/README.md). Bodies over 1 024 000 bytes are spooled to `/userdata/WifiFile/tmp_files`, which the image does not create **[I]**. The UI watches the directory and refreshes the Wi-Fi file list on its own.

`execute_code` exists in the slicer's client and was accepted in the 2026-11-01 live test (one G-code line). It is not one of the six routes recovered from `printer_http_api.so`; treat the live result as the observation and the `.so` map as the routes found in that binary.

## Update package

Settings → Update Firmware scans `/Local` (a partitioned USB stick; the automounter only mounts `sd[a-z][1-9]+`, so an unpartitioned stick does not appear). The search is the top directory only. The zip name must contain both `IVI3DPrinterFirmwarePack` and `zip`, case-sensitive **[V]**.

```
Firmware/firmware          UI binary
Firmware/config.ini        version=<float>, MD5=
Firmware/firmware.supx     optional motion image
Firmware/config2.ini       optional motion MD5 and version
printer_http_api/          copied before the MD5 and version checks
script/                    copied before the checks (can replace autorun.sh)
```

Integrity is MD5 only. There is no signature. Touchscreen update runs when the package version float is greater than the **1.222 compiled into the running binary**. Controller update runs when both `firmware.supx` and `config2.ini` match, including a same-version re-flash. The controller is updated first. The UI reboots about two seconds after success.

The motion image is applied by the STM32 bootloader, not by this script. `M997` resets the controller into that bootloader; it then erases and programs sectors 4–5 only, and a CRC failure or a power loss mid-update leaves it waiting for a full re-send. USB-C can reach the same bootloader without the A33 (confirmed 2026-11-10); the write stream itself has not been sent that way. Frame replies, the EEPROM pending record, and the gentler recovery order: [stm32.md](stm32.md#update-protocol).

`unzipFirmware.sh` overwrites `printer_http_api/` and `script/` before those checks. There is no backup of `IVI-Main-Controller` inside the script.

The beta-program PDFs describe the lid ports and do not contain an update procedure.

## Recovery, short version

While the rootfs still boots, the ttyS2 root shell can copy a known-good `firmware` binary back onto `IVI-Main-Controller` from a stick. Repartitioning, `saveenv`, FEL writes, and restoring p7 while it is mounted are not authorized. The backup that exists, and the routes that would use it, are in [backups.md](backups.md).

## Rescue kit

[tools/a33_rescue/](../tools/a33_rescue/README.md) is an offline-built FEL and microSD rescue system. It has not been run on this board. The safest path is FEL plus a RAM boot: U-Boot, the kernel, and the initramfs are loaded into DRAM over USB, and nothing is written to storage until a later command says so. Steps are labelled **R0** (read only) through **W4** (whole eMMC user area). The userspace scripts were checked under QEMU only. The hardware verification list in the runbook is still open, including how to enter FEL, whether the micro-USB port is the A33 OTG port, and whether mainline DRAM init matches this board. W3 and W4 stay unauthorized. Runbook: [RESCUE.md](../tools/a33_rescue/RESCUE.md). Build: [BUILD.md](../tools/a33_rescue/BUILD.md).
